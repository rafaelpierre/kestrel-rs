# Issue #34: initial investigation

Issue: https://github.com/rafaelpierre/kestrel-rs/issues/34
Base: `95899d1`; branch: `codex/issue-34-provider-diagnostics`.

## Findings at the starting commit

- `src/model.rs`, `ProviderSearchDiagnostic`: one provider/query summary,
  with no run/search/attempt IDs or structured HTTP and transport observations.
- `src/search.rs`, `run_one`: attempt counts live in task-local atomic state
  but are copied into the summary only after the awaited job returns. Quorum
  drops skip that copy. `DiagnosticTimer` retains elapsed time alone.
- `run_one` starts timing before semaphore acquisition. Its elapsed time mixes
  queueing, network, body read, parsing and backoff. The default cancellation
  outcome assumes quorum, so generic caller cancellation is indistinguishable.
- `search_yahoo` captures successful bodies only; failed statuses discard bodies.
  The standard retry helper captures failed bodies but silently replaces body-read
  errors with empty strings. Both lose response metadata on successful-status
  body-read failures.
- HTTP errors return before challenge parsing. A 403 challenge therefore becomes
  `request_error`; neither retry helper records Retry-After or redirect hops.
- `capture_provider` uses unrelated random filenames; they cannot reliably join
  attempt records to final outcomes. Raw tracing is opt-in but currently includes
  query, URL and HTML: do not assume those values are already redacted.
- `DiagnosticTimer::drop` persists while holding the diagnostic mutex. Issue #17
  owns replacing that synchronous persistence path.
- Existing mocks cover successful-status challenges and quorum result ordering,
  but do not verify attempt accounting through cancellation. `retry_delay` skips
  sleeping in unit tests, so backoff-cancellation tests need a controllable delay.

## Proposed implementation boundary

1. Add internal, versioned logical-search and send-attempt records, preserving
   normal result JSON. Allocate run and logical-search IDs before futures are
   polled; give each send a distinct attempt ID and ordinal. A logical search
   means one scheduled provider/query operation. Explicitly label counts as
   application sends, not wire requests (automatic redirects may add requests).
2. Keep phase and attempt state in a shared recorder owned by a cancellation
   guard. Update before each await: queued, sending, reading body, parsing,
   backoff. Record HTTP status and Retry-After immediately on headers, before
   reading the body. Retain typed errors, including body errors; distinguish
   timeout/connect/TLS only where backend evidence supports it, otherwise unknown.
3. Classify challenge independently as detected/not_detected/unknown, including
   failed HTTP responses. Missing or unreadable content must remain unknown.
   Preserve retry policy while adding observations.
4. Measure queue, send-to-headers, body, parse and backoff separately. For an
   interrupted phase, retain elapsed lower bound with a censored flag. Completed
   phases and earlier attempts remain completed even when the logical search
   later hits deadline or quorum. Cancellation during backoff creates no new send.
5. Finalize each logical record once. Pre-register even never-polled jobs, and
   propagate explicit deadline/quorum/caller cancellation reason. Copy completed
   snapshots outside locks to the persistence boundary supplied by #17; do not
   implement another writer or spawn one task per record here.
6. Route Yahoo failed bodies through the existing opt-in trace policy and attach
   correlation IDs. Define an explicit safe metadata allowlist rather than copying
   all response headers (especially cookies or credentials).

## Verification to implement

- Mock 200 and 403 challenges; 429 with Retry-After; recovery and exhaustion;
  transport and body failures. Exercise both request backends with injectable
  endpoints or adapters, without contacting live providers.
- Deterministically interrupt before polling, while queued, during send/body,
  and during backoff, for deadline and quorum; cover caller cancellation too.
- Assert logical totals equal terminal logical outcomes, and sends equal terminal
  attempt records (completed or interrupted). Retries equal started sends minus
  one, floored at zero. A failed attempt followed by recovery is not a logical
  failure; a completed 500 followed by cancelled backoff remains a completed 500.
- Verify censored intervals are excluded from completed latency samples, IDs join
  trace files correctly, trace opt-out produces no raw files, and ordinary result
  JSON is unchanged. Coordinate slow-sink/overflow tests with #17.

## Implementation completed

- Added an internal versioned logical-search/attempt schema with shared run IDs,
  unique search/attempt IDs, an optional benchmark label and explicit
  application-send counting (redirect hops are not observed).
- Both HTTP backends retain final headers, Retry-After, independent challenge
  classification and typed transport/body errors. Failed Yahoo bodies use the
  same opt-in raw capture path and correlation metadata as other providers.
- Fanout registers jobs before polling; dropped futures retain retry counts,
  cancellation reason and phase, including never-polled and queued jobs.
  The single-provider entry point and selected fallback providers also record
  diagnostics. Unselected fallback providers are not scheduled searches.
- Deadline/cancellation and client timeout intervals are censored. Completed
  attempts survive cancellation during later backoff. Queue, send, body, parsing,
  processing and backoff are distinct intervals.
- Preserved public report/result shapes, including the single-provider API's
  existing provenance behavior. Structured records are confined to opt-in traces.
- Snapshots leave both mutexes before persistence. The existing synchronous sink
  remains the integration boundary for #17; no competing file writer was added.
- Documented counting, classification, privacy and timing in
  `docs/provider-diagnostics.md` and linked it from the provider guide.

## Verification

All-target tests pass (80 tests: 57 library, 4 binary, 19 integration). The new
mocked coverage exercises both backends for 200/403 challenges, 429/Retry-After,
retry recovery/exhaustion, connection errors, incomplete bodies, client timeouts,
redirect count labeling, trace correlation, and deadline interruption during
body/backoff. Lifecycle tests cover never-polled and queued drops, caller/quorum
reasons, shared run IDs, and real-response quorum cancellation during backoff.
Typed TLS classification uses both backend error types; no live TLS/provider
availability claim is made. Clippy with warnings denied and formatting checks
are part of final validation.

## Remaining integration boundary

Issue #34's semantics are implemented. Issue #17 still owns nonblocking storage,
overflow handling, and flush/shutdown guarantees. Trace writes remain best effort
and synchronous; abrupt process termination or persistence failures can lose
files. No live Yahoo pilot was repeated. Changes remain local and uncommitted.
